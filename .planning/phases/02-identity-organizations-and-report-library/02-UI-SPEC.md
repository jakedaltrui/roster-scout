# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — existing custom CSS and server-rendered Jinja templates |
| Preset | not applicable; this is a Flask/vanilla-JS application, not React/Next/Vite |
| Component library | none; use semantic HTML and small progressive-enhancement modules |
| Icon library | existing inline outline SVG style, 20px default, `currentColor`, 1.7–2px stroke; no new icon package |
| Font | DM Sans, system sans-serif fallback; use only 400 and 600 in the authenticated product UI |

The authenticated workspace must remain visually continuous with the existing Roster Scout site: keep the outlined dog mark, lowercase wordmark, DM Sans, light/dark theme preference, quiet neutral surfaces, rounded controls, thin borders, and restrained motion. Do not copy the marketing page's oversized hero typography into product screens. The product shell is denser and optimized for repeated use during a series.

Hosted WorkOS AuthKit is the credential UI. Configure its available brand controls with the Roster Scout mark, product name, and neutral/forest palette. The local application supplies only the branded transition, callback/error, invitation, organization-selection, and no-membership screens; it must not recreate provider passwordless, Google, Microsoft, SAML, or OIDC forms.

## Information Architecture and App Shell

### Route-level experience

1. An unauthenticated visitor can see the public brand/sign-in transition but cannot see team search, report content, status, history, or downloads. The primary action is `Sign in to Roster Scout` and immediately hands off to hosted AuthKit.
2. A successful callback with one active membership opens that organization's report library.
3. A successful callback with multiple memberships opens organization selection on first sign-in; subsequent sessions restore only a still-active selection.
4. An authenticated account with no membership sees the no-membership state, plus `Sign out`; it has no report or selector controls.
5. A user following an invitation returns to a local acceptance outcome after hosted sign-in. Exact-email mismatch, expired, used, and revoked outcomes use fixed messages without revealing another recipient or organization data.

### Authenticated header

- Sticky, 64px desktop / 56px mobile, using the existing pill-header visual language without the marketing section links.
- Left: Roster Scout logo and wordmark linked to the active organization's report library.
- Center desktop navigation: `Reports`; `Members` only for admins. `Create report` is a high-salience action but appears once, right of navigation.
- Right: organization switcher, theme toggle, and account menu with verified email plus a CSRF-protected `Sign out` form.
- Mobile: logo, truncated organization switcher, and one menu button. The opened menu contains Reports, Members when authorized, Create report, theme control, account email, and Sign out. Focus returns to the menu button on close.
- Never display an organization UUID, provider organization, role claim, or browser-supplied organization ID.

Use one `<main>` with a visible page title and a skip link. Breadcrumbs are required on report detail (`Reports / {Opponent}`), create report (`Reports / Create report`), and membership administration (`Reports / Members`).

## Authentication and Invitation Transitions

### Sign-in transition

- Local page title: `Sign in to Roster Scout`.
- Body: `Use your work email to access your organization’s opponent reports.`
- Primary action: `Continue to sign in`.
- Supporting note: `Passwordless email, Google, Microsoft, and your organization’s SSO may be available.`
- Do not present a password field, individual local provider buttons, or an email field. AuthKit owns those controls and its recovery/rate-limit UX.
- Preserve a same-origin allowlisted return destination only. While redirecting, show a single `Opening secure sign-in…` status. Do not display or echo callback parameters.

### Callback and failures

- Normal callback has no interstitial; redirect to organization selection, invitation outcome, or report library.
- Sanitized local failure heading: `We couldn’t sign you in`.
- Body: `Return to sign in and try again. If the problem continues, contact support.`
- Primary action: `Return to sign in`. Do not expose provider error text, codes, assertions, tokens, raw query parameters, or stack traces.
- A transient provider refresh failure keeps the current local session and surfaces a non-blocking banner: `Sign-in services are temporarily unavailable. Your current session is still active.`
- A terminal/revoked session redirects to sign in with: `Your session ended. Sign in again to continue.`

### Invitation acceptance outcomes

| Outcome | Heading | Body / action |
|---------|---------|---------------|
| accepted | `You joined {organization}` | `You can now review and create reports with your staff.` Action: `Open reports`. |
| email mismatch | `This invitation can’t be accepted` | `Sign out and use the exact email address that received the invitation, or ask an administrator to send a new one.` Do not print the invited address. |
| expired/revoked/used/invalid | `This invitation is no longer available` | `Ask an organization administrator to send a new invitation.` |
| provider unavailable | `Invitation sign-in is temporarily unavailable` | `Try again in a few minutes. The invitation has not been used.` |

## Organization Selection and Switching

- Organization selection is a centered list of the account's active local memberships. Each row/card shows organization name and local role (`Admin` or `Member`) with one `Open organization` action.
- Do not show email-domain suggestions as memberships. Optional suggested organizations, if ever present, must be visually separated under `Suggestions` and can only instruct the user to request an invitation; Phase 2 does not add a request-access workflow.
- The header switcher button reads the active organization name, truncates after 28 characters, and exposes the full name in accessible text/title. Its menu lists active memberships only, marks the current one with `Current`, and ends with no organization-creation control.
- Switching uses a CSRF-protected POST, rotates the local session, then lands on the target organization's report library. Do not preserve a report/job/snapshot identifier across organizations.
- If the active membership disappears, the next protected request clears it and routes to organization selection or the no-membership state with: `Your access to that organization changed. Choose another organization to continue.`

## Report Library

### Page header and controls

- Visual focal point: the report list is the dominant content surface, with `Create report` as its single high-salience companion action. Organization totals and navigation remain visually subordinate; do not introduce a dashboard summary that competes with the list.
- Page title is the active organization name; eyebrow/section label is `Opponent reports`.
- Primary action is `Create report`.
- Secondary summary uses plain totals, e.g. `18 reports · 3 updated today`; it is not an analytics dashboard.
- Paginate 25 reports per page using server-rendered previous/next links. Preserve no client-only sort state. Initial order is most recently created or refreshed first, then opponent name.

### Desktop table (`min-width: 768px`)

Use a real `<table>` with caption `Opponent reports for {organization}` and these columns in order:

1. `Opponent` — logo/fallback initials, full school name, division and season subline.
2. `Latest snapshot` — localized date/time; `No snapshot yet` when the first build is active or failed.
3. `Completeness` — Ready, Partial, or `—`; partial includes unavailable-section count.
4. `Build status` — Queued, Collecting, Saving, Failed, or `No active build`.
5. `Snapshots` — numeric count.
6. Unlabeled action column — `Open report`; this is also the row's single primary navigation target. Do not make the entire row a nested clickable control.

Rows are 64px minimum, with a neutral hover/focus-within surface. The latest published snapshot and active job are separate fields; a refresh must never replace the displayed latest timestamp with a spinner.

### Mobile cards (`max-width: 767px`)

- Render the same server-provided fields as a `<ul>` of cards; do not fetch a different mobile model.
- Card order: opponent + division/season, latest snapshot, completeness/build-status chips, snapshot count, full-width `Open report`.
- A card may omit column labels only when the meaning remains explicit. `Latest snapshot`, `Build status`, and `Snapshots` labels remain visible.
- Cards use 16px gaps, 16px padding, and one column. No horizontal table scrolling is permitted for the report library.

### Library states

- Empty state uses the specified copy and `Create report` action. Include the dog mark as a quiet monochrome 48px brand element, not an illustration dependency.
- A filtered/secondary empty state is out of scope because Phase 2 does not require report search or filters.
- Library load failure is a page-level error with `Try again`; never render an empty library when the database failed.

## Create Report Flow

- Use a separate server-rendered `/reports/new` page so reload/back/validation states are stable. Place the form in a 560px maximum-width card.
- Heading: `Create opponent report`. Body: `Choose an exact NCAA team. Roster Scout will collect live data and save a dated snapshot for your organization.`
- Reuse the current selector contract and interaction: D1/D2/D3 segmented group, typeahead school combobox, current catalog year, NCAA season-team identity, NCAA logo endpoint, keyboard arrows, Home/End where applicable, Enter to select, Escape to close, and visible exact selection.
- The typed string is never sufficient. The CTA remains disabled until a catalog option is selected; any edit after selection clears the hidden identity and returns the field to unselected state.
- Catalog loading copy: `Loading the current NCAA catalog…`; empty query result: `No matching NCAA teams`; catalog failure: `We couldn’t load NCAA teams. Try again.` with `Retry catalog`.
- Primary action: `Create report`. Secondary action: `Back to reports` returning to the library.
- On submit, disable both controls, preserve the selected team label, and show `Accepting report request…`. Do not simulate collection progress on this page.
- After the authorized durable job is accepted, redirect to report detail. Repeated submission or an existing active job converges on that report/job and uses `A build is already in progress. Showing its current status.`
- Validation failure focuses the first invalid control and uses an inline message plus summary: `Choose an NCAA team from the list.`
- Phase 2 does not add JUCO creation, free-text fallback, split selection, last-10/conference switches, metrics, or output-format options.

## Report Detail and Snapshot History

### Stable page structure

- Visual focal point: the newest published snapshot is the dominant panel and remains the page's visual anchor. An active refresh is a compact subordinate status panel; it must not displace, dim, cover, or visually outweigh the saved snapshot.

1. Breadcrumb and opponent header: logo, full school name, division, season.
2. Action group: `Refresh report`; `Download snapshot` only when the selected/latest published snapshot has an authorized bound artifact.
3. Active build panel, only when a job is queued/running/retrying or the latest attempt failed.
4. Latest published snapshot panel, always retained while refresh runs. Show `Latest snapshot`, exact captured/published time, Ready/Partial, source freshness, and predecessor lineage when present.
5. Section status list using only server-provided Phase 2 section names. Do not invent Phase 3 sections or promise fielding, splits, career data, game logs, last-10, or conference data.
6. `Snapshot history`, newest first, 25 per page.

### Active build panel

- Use a status heading, timestamp, and ordered progress list when the backend exposes real section state. Do not advance illustrative timers.
- Every progress row contains a text state (`Waiting`, `Collecting`, `Ready`, `Unavailable`, `Failed`) and optional safe explanation. The UI may summarize source/database/queue/artifact categories but never raw upstream or exception text.
- `aria-live="polite"` announces only state transitions. A visually hidden live region says, for example, `Refresh status changed to Saving snapshot.` It does not announce every poll.
- An active refresh includes: `Your {timestamp} snapshot remains available while this refresh runs.`

### Snapshot history

- Desktop uses a table; mobile uses equivalent cards. Fields: captured date/time, completeness, source freshness, predecessor (`Initial snapshot` or `Refresh of {date}`), artifact status, and action.
- The newest Ready or Partial snapshot is marked `Latest`. Failed jobs remain in a separate `Build attempts` region or active-build history; they must not appear as snapshots or receive download actions.
- `View snapshot` routes to the immutable snapshot context. `Download snapshot` resolves that exact authorized snapshot artifact; never silently rebuild or substitute the latest artifact.
- If an artifact is absent, show `Download unavailable` as text with the required explanation. A disabled button alone is insufficient.

### Partial snapshot

- Place a warning banner immediately below the snapshot title: `Some data is unavailable in this snapshot.`
- Body: `You can still review the saved sections. Unavailable: {exact section list}.`
- Ready sections remain accessible. The snapshot remains in history and can expose its bound artifact if one exists.
- Do not label a Partial snapshot Ready, and do not convert unavailable sections to zeros or blank success states.

### Failed build and retry

- Show a failed alert above, not instead of, the previous published snapshot.
- Copy: `We couldn’t create a new snapshot. Your previous snapshot is unchanged.` Add attempted time and one fixed safe category: `NCAA source unavailable`, `Report service unavailable`, `Storage unavailable`, `Sign-in service unavailable`, or `Something went wrong`.
- Primary action: `Retry build`. It accepts a new linked attempt; its pending state is `Accepting retry…`, then the page returns to polling. Preserve the failed attempt in build history.
- If retry acceptance fails, restore the enabled control and focus a fixed inline error. Never optimistically hide the failed attempt.

## Explicit Refresh Contract

- `Refresh report` never starts collection immediately. It opens an accessible confirmation dialog; without JavaScript it links to an equivalent server-rendered confirmation page.
- Dialog title: `Refresh {opponent}?`
- Body: `This collects live NCAA data and creates a new snapshot. Your {latest snapshot date and time} snapshot will stay unchanged.`
- If no published snapshot exists, use: `This starts a new live collection. Failed attempts will remain in the build history.`
- Primary action: `Start live refresh`. Secondary action: `Keep current snapshot`.
- On confirm, disable the primary action and label it `Starting refresh…`. On durable acceptance, close/redirect and move focus to the active build heading.
- If a job is already active, do not show a second confirmation. Replace the refresh action with `View refresh status` and announce `A refresh is already in progress.` Duplicate network submissions attach to that active job and never show two progress panels.
- Refresh language must not imply the previous snapshot changes, expires, or is overwritten. It must not mention cache internals.

## Polling and Progressive Enhancement

- Server-render the full report detail first. `static/report_status.js` enhances only the active build/status regions.
- Poll the organization-scoped status endpoint every 3 seconds for the first 30 seconds, every 5 seconds through 2 minutes, then every 10 seconds through 15 minutes.
- Stop on Ready, Partial, or Failed; pause while `document.hidden`; resume with one immediate poll when visible. After 15 minutes, stop automatic polling and show the `Still working` state with `Check status`.
- Each response must be treated as a complete safe view model. Update text, chips, progress, and actions together; do not infer Ready from HTTP 200 or elapsed time.
- Network errors back off to the next cadence and show a non-blocking `Status temporarily unavailable` note after two consecutive failures. Do not change the durable job state in the UI.
- The status region works after reload with no client memory. Poll URLs contain only scoped opaque resource identifiers, never organization or role authority.
- Respect `prefers-reduced-motion`; status updates use opacity/color changes only, no perpetual animated progress except one small spinner while an immediate form submission is awaiting acceptance.

## Membership Administration

### Page structure

- Admin-only navigation label and page title: `Members`.
- Intro: `Manage who can access {organization} and its shared reports.`
- Sections in order: invite form, active members, pending invitations. Each section has an explicit count.
- Members and invitations use compact desktop tables and equivalent mobile cards at 767px, matching the report-library responsive pattern.

### Invite form

- Fields: `Email address` and `Role`; role defaults to `Member` with options Member/Admin.
- Help: `Any valid email address can be invited. School email is not required.`
- Primary action: `Send invitation`.
- Success flash: `Invitation sent to {email}. It expires {date}.`
- Existing pending invite: `An active invitation already exists for this email.` Provide `Resend invitation` only if the backend safely supports provider re-delivery without generating ambiguous active invites; otherwise show `Revoke invitation` then allow a new invite.
- Normalize/validate on the server. Do not imply a domain grants access.

### Members

- Fields: name or verified email, role, joined date, status, actions.
- Current account is labeled `You`. Last active admin row shows `Last admin` and its remove/demote controls are disabled with visible text: `Add another admin before changing this role.`
- Role changes use a labeled select plus `Save role`, not an instant-change dropdown. Changing an Admin to Member uses confirmation: `Change {name} to Member? They’ll no longer manage invitations or members.`
- The demotion confirmation actions are `Change to Member` and `Keep admin`. Remove-member confirmation actions are `Remove member` and `Keep member`.
- Remove uses the destructive confirmation copy. On success, remove the row and announce `{name} was removed from {organization}.`

### Pending invitations

- Fields: email, role, invited by, sent date, expiry, status, actions.
- Pending rows offer `Revoke invitation`. Expired/revoked rows are retained only if the product read model includes them; they are neutral history and have no action.
- Revocation uses the destructive style and confirmation copy. Its actions are `Revoke invitation` and `Keep invitation`. Never expose provider invitation IDs or acceptance secrets.

Non-admin members do not see the Members navigation or invite/member controls. A direct request receives a fixed permission response; it must not leak other member or invitation data.

## Error, Security, and Disclosure States

- Missing and foreign report, job, snapshot, artifact, refresh, retry, status, and download identifiers render the identical 404 page and identical JSON error shape. The HTML copy is the generic `Page not found` contract above. Do not distinguish `does not exist`, `belongs to another organization`, or `you do not have access`.
- Role-denied organization administration uses `You don’t have permission to manage members.` with `Return to reports`; it includes no member or invitation data.
- CSRF/session expiry uses `Your session ended. Sign in again to continue.` Preserve no unsafe POST for automatic replay.
- Sanitized operational states are distinct: identity unavailable, database/report service unavailable, queue/build service unavailable, NCAA source unavailable, and artifact/storage unavailable. Each tells the user whether to retry, check status, or contact support, without raw exceptions.
- Flash banners use `role="status"` for success/information and `role="alert"` for blocking errors. They persist until the next navigation or explicit dismissal; auto-dismiss is prohibited.
- Customer pages never expose actor IDs, organization IDs, WorkOS IDs, job IDs, snapshot IDs, audit event details, stack traces, provider errors, tokens, invitation secrets, source payloads, or exception text.

## Accessibility Contract

- Meet WCAG 2.2 AA for contrast, keyboard operation, focus visibility, reflow, labels, errors, and status announcements.
- Every page begins with `Skip to content`; use semantic header/nav/main/footer landmarks and one `<h1>`.
- Visible focus is a 3px accent outline with 3px offset in both themes. Never remove focus without a replacement.
- All interactive targets are at least 44×44px. Icon-only buttons require visible tooltip/title and accessible name; destructive actions retain visible text in menus/dialogs.
- Exact NCAA selection follows the ARIA combobox/listbox pattern already used: input owns `aria-controls`, maintains `aria-expanded`/active descendant, and selection is announced. Division is a labeled pressed-button group.
- Desktop data structures use real tables with captions and `<th scope>`; mobile cards use lists with visible field labels. CSS must not convert the same DOM table into inaccessible display blocks; render equivalent server-side markup from one view model.
- Dialogs have labelled title/description, trapped focus, Escape close, and focus restoration. Initial focus is outcome-specific: `Keep member`, `Keep admin`, or `Keep invitation` for destructive confirmations, and `Keep current snapshot` for refresh. The user must deliberately move focus to the consequential action.
- Field errors are adjacent, linked with `aria-describedby`, and summarized above the form. Focus the summary on failed POST, then allow links to invalid fields.
- Polling announces transitions only. Spinner and decorative icons are `aria-hidden`; text carries every state. Ready/Partial/Failed are never encoded by color alone.
- Theme control has a stateful accessible label (`Switch to dark mode` / `Switch to light mode`) and follows the existing storage-failure-safe behavior.
- With reduced motion, remove transform/scroll/reveal animations and animated progress. Functional status remains unchanged.

## Out-of-Scope Guardrails

Phase 2 UI must not expose placeholders, disabled navigation, or promotional promises for:

- Fielding, derived metrics, splits, career history, or game logs.
- Last-10 or conference-only scopes.
- The Phase 4 ten-sheet detailed workbook.
- Power BI, dashboards, embedded analytics, RLS, or embed tokens.
- Public organization signup, domain-based auto-join, request-access workflow, cross-organization sharing, notes, or report comparison.

The report library may display only data and artifacts the Phase 1/2 backend can truthfully provide. Later phases extend the detail content without changing this shell, snapshot, refresh, or organization interaction contract.
